# 실무 실습 사이트 설계

> 상태: **방향 확정** (2026-11-10). 목표·단계는 [00-overview.md](../00-overview.md), 구조 결정은 ADR-0012~0015에 반영했습니다. §13의 2~5번은 아직 제안입니다.

## 1. 무엇을 바꾸나

**회계 ERP를 만드는 프로젝트에서, 그 ERP로 회계팀 신입이 실무를 처음부터 끝까지 연습하는 사이트로.**

ERP는 버리지 않습니다. 지금까지 만든 것과 앞으로 만들 엔진(장부, 부가세, 결산)은 그대로 **바닥**이 되고, 그 위에 **실습 층**을 얹습니다.

| | 지금 | 전환 후 |
| --- | --- | --- |
| 사용자 | 저장소 주인 (만들면서 배움) | 이론은 배웠지만 실무는 처음인 회계팀 신입 |
| 들어오면 보이는 것 | 로그인 → 빈 ERP 메뉴 | "입사 첫날" → 오늘 할 일 → 증빙 → ERP 화면 |
| 완료의 뜻 | 1년치 거래가 재무제표까지 맞게 나온다 | **사용자가** 1년치 업무를 직접 처리해 재무제표까지 만든다 |
| ERP의 역할 | 결과물 | 실습 도구이자 채점 기준 |
| 시나리오 회사 | 골든 테스트용 데이터 | 실습 과정의 줄거리 |

## 2. 누구를 위한 것인가

**대상**: 제조업 중소 법인 회계팀에 막 들어온 신입. 전산회계 수준의 분개는 할 줄 알지만 다음이 낯섭니다.

- 문제지가 없다. **증빙**(세금계산서, 카드전표, 통장 내역, 지출결의서)을 보고 스스로 거래를 읽어야 한다
- 전표를 치면 끝이 아니다. **결재 → 전기 → 장부 확인 → 대사 → 마감 → 신고**로 이어진다
- 틀리면 지우는 게 아니라 **정정 절차**(역분개)가 있다
- 일이 **달력**을 따라 온다 (매월 10일 원천세, 분기 25일 부가세, 월 마감, 연 결산)
- ERP 화면과 용어 자체가 낯설다 (전기, 미결, 거래처원장, 유형 51·54 …)

**시험 준비 프로그램과 다른 점**: 시험은 "문장으로 된 거래 → 전표"를 묻습니다. 여기는 "증빙 묶음과 상황 → 판단 → 전표 → 그 뒤의 업무 전체"를 겪게 합니다.

**가르치는 것**: 특정 ERP 제품의 사용법이 아니라 **업무 흐름**. 화면은 국내 회계 프로그램의 공통 관례(구분 1~4, F2 코드 도움, 매입매출 유형 번호)를 따르므로 어떤 제품을 쓰게 되어도 옮겨 갈 수 있습니다.

## 3. 사용자가 겪는 흐름

1. **입장**: 가입 없이 "체험 시작" → 나만의 실습 회사 (주)엠제트전자가 만들어진다 (30초 이내)
2. **입사 첫날**: 팀장의 환영 메시지, 회사 소개, 회계팀의 1년 달력, 메뉴 둘러보기
3. **받은 업무함**: 오늘 날짜(시뮬레이션 날짜)와 처리할 일이 쌓여 있다
4. **미션 하나**: 상황 읽기 → 증빙 열기 → ERP 화면에서 실제로 처리 → **결재 요청**
5. **결과**: 맞으면 팀장이 승인(전기)하고 "왜 이 분개인가" 해설이 열린다. 틀리면 **반려 사유**가 온다 ("세액 1,000,000원이 원재료 금액에 들어가 있어요")
6. **장이 끝나면**: 장부에서 결과를 확인하는 점검 미션, 그리고 다음 달로
7. **끝**: 결산 → 재무제표 완성 → 수료 리포트 (어떤 유형에서 자주 틀렸는지)

안내의 강도는 뒤로 갈수록 줄입니다.

| 단계 | 안내 | 쓰는 곳 |
| --- | --- | --- |
| 따라 하기 | 누를 곳을 화면에 표시, 칸마다 설명 | 0~1장 초반 |
| 업무 | 증빙과 상황만 제공, 힌트는 요청할 때만 | 대부분의 미션 |
| 실전 | 힌트 없음, 한 달치를 모아서 처리하고 마감 때 한 번에 채점 | 마지막 장 |

시나리오 회사의 2026년을 따라갑니다. 기존 [거래 38건 + 결산 9건](../scenario/journal-2026.md)이 대부분 미션으로 바뀝니다.

| 장 | 실무 상황 | 미션 예 | 기존 시나리오 | 필요한 ERP |
| --- | --- | --- | --- | --- |

### 미션 유형

| 유형 | 사용자가 하는 일 | 채점 |
| --- | --- | --- |
| 전표 입력 | 증빙을 보고 전표 작성 → 결재 요청 | 장부 변화가 기대와 같은가 (§7) |
| 장부 판독 | 원장·시산표에서 숫자를 찾아 답 입력 | 정답 장부의 값과 비교 |
| 대사 | 두 자료(통장↔장부, 합계표↔장부)의 차이를 찾아 해소 | 차이가 0이 되었는가 |
| 오류 정정 | 잘못 전기된 전표를 찾아 역분개 + 올바른 전표 | 최종 잔액 + 원전표가 남아 있는가 |
| 절차 | 마감·신고처럼 순서가 있는 일 | 각 단계의 상태 (기간 CLOSED, 정리 전표 존재 …) |
| 개념 확인 | 짧은 선택형 질문 | 정답 비교. 장마다 2~3개 이내로 제한 |

```
│             │                              [결재 요청]    │ ☐ 결재 요청         │

└─────────────┴─────────────────────────────────────────────┴─────────────────────┘
```

- **ERP 화면은 실습용으로 따로 만들지 않습니다.** 자유 모드에서 쓰는 화면과 같은 화면에 미션 패널만 붙습니다. 그래야 "연습한 화면 = 실제 화면"입니다.
- **증빙 뷰어**: 전자세금계산서, 계산서, 카드 매출전표, 현금영수증, 간이영수증, 거래명세서, 통장 거래내역, 지출결의서, 급여대장, 어음. 미션 데이터로 그리는 문서 컴포넌트이며 모두 "실습용" 표시를 넣습니다.
- **용어 사전**: 화면의 낯선 용어에 밑줄 → 2~3문장 설명 + "이론에서는 이렇게 배웠죠" 연결.
- **자유 모드**: 미션 없이 ERP만 쓰는 모드. 지금의 MZ-ERP가 그대로 이 모드가 됩니다.

## 6. 구조

```
┌──────────────────────────────────────────────────────────────┐
│ 실습 층 (learning)   과정·미션·채점·진행도·증빙·게스트 입장    │
│        │ ERP의 공개 서비스만 호출 (JournalService, 장부 조회) │
│        ▼                                                      │
│ ERP 층   전표 · 장부 · 부가세 · 결산 · 재무제표 · 기준정보    │
│        ▼                                                      │
│ DB       회계 불변식을 지키는 제약·트리거                     │
└──────────────────────────────────────────────────────────────┘
```

- **의존은 한 방향**: 실습 층 → ERP 층. ERP 코드는 실습 층을 모릅니다. ArchUnit으로 강제합니다 ([ADR-0012](../adr/0012-learning-layer-on-top-of-erp.md)).
- **채점 때문에 불변식을 느슨하게 하지 않습니다.** 실습 중에도 전기된 전표는 못 고치고, 마감된 달에는 못 넣습니다. 그 제약을 겪는 것이 실습 내용입니다.

### 실습 회사 = 회사 한 개 복제

모든 테이블에 `company_id`가 있으므로, 사용자마다 회사를 하나씩 만들어 주면 서로 섞이지 않는 실습 공간이 됩니다. 새 테넌시 구조가 필요 없습니다.

- 과정 시작 → 표준 계정표 복사 + 거래처 등록 + 회계연도 + 기초잔액 전표
- 사용자는 그 회사에서 작성자(WRITER) 권한, **팀장은 시스템 계정**(승인자). 9장에서 사용자가 승인자로 올라갑니다

### 시나리오 리플레이어 — 하나로 세 가지

시나리오 파일의 거래를 `JournalService`로 순서대로 넣는 엔진입니다.

| 쓰임 | 설명 |
| --- | --- |
| 골든 테스트 | 처음부터 끝까지 재생 → 장부가 [정답](../scenario/answers-2026.md)과 같은가 (`ScenarioGoldenTest`, 구현됨) |
| 체크포인트 | 3장을 시작할 때 2장까지가 맞게 처리된 회사를 만들어 준다. 앞 장에서 틀려도 뒤가 연쇄로 틀리지 않게 하고, "이 장부터 다시"를 가능하게 한다 |
| 정답 대신 처리 | 막혔을 때 "정답 보고 넘어가기" → 시스템이 그 미션의 전표를 넣는다 |

### 콘텐츠는 저장소 파일

미션은 DB가 아니라 `data/course/*.toml` + 해설 Markdown으로 둡니다. 지금의 시나리오 파일을 확장한 형태입니다.

```toml
[[missions]]
key      = "purchase-raw-material"
chapter  = "ch2"
date     = 2026-01-20
title    = "원재료 외상 매입"
scenario = 3                        # 시나리오 거래 #3과 연결 → 정답 분개를 거기서 가져온다
brief    = "missions/purchase-raw-material.md"
documents = [{ type = "TAX_INVOICE", supplier = "00201", supply = 10000000, tax = 1000000 }]
accept   = []                       # 정답으로 인정하는 다른 분개
hints    = ["세금계산서의 공급가액과 세액은 서로 다른 계정으로 갑니다", "아직 돈을 주지 않았습니다"]
concepts = ["부가세대급금", "외상매입금"]
```

- 리뷰·이력 관리가 코드와 같고, CI가 모든 미션을 검증합니다 (§9)
- DB에는 **사용자 상태**(누가 어디까지 했나)만 저장합니다

## 7. 채점

### 입력이 아니라 장부의 변화를 본다

키 입력이나 화면 단계를 비교하지 않습니다. **미션 시작 시점의 잔액과 지금 잔액의 차이**가 기대한 차이와 같은지 봅니다.

```
기대 변화 = { (153 원재료): +10,000,000,  (135 부가세대급금): +1,000,000,
              (251 외상매입금, 대성소재): +11,000,000 }
실제 변화 = 지금의 계정·거래처별 잔액 − 미션 시작 때 저장해 둔 잔액
```

- 줄 순서, 적요, 전표를 한 장으로 쳤는지 두 장으로 나눴는지는 상관없습니다
- **틀리게 전기했다가 역분개하고 다시 넣어도 통과**합니다. 실제 업무에서 올바른 처리이기 때문입니다
- 불변식 5(장부는 전표 라인에서만 파생)가 그대로 채점의 근거가 됩니다
- ERP 테이블에 실습용 컬럼을 추가하지 않습니다. 시작 시점 잔액은 실습 층이 따로 저장합니다

잔액만으로 안 되는 것은 추가 검사로 봅니다: 전표 일자 = 증빙 일자, 부가세 유형, 공급가액·세액, 전기 여부, (오류 정정 미션에서) 원전표가 지워지지 않고 남아 있는지.

### 결재 요청 = 채점

사용자가 임시 전표를 올리면 팀장(시스템)이 검토합니다.

- 맞음 → 팀장이 **전기**하고 해설을 연다
- 틀림 → **반려**. 전표는 임시 상태로 남아 고칠 수 있다
- 1장 뒤로는 사용자가 직접 전기할 수 있는 미션을 섞습니다. 틀리게 전기하면 역분개로 정정해야 통과합니다

채점이 "정답/오답" 팝업이 아니라 실제 업무의 결재 흐름으로 보이게 하는 장치입니다.

### 반려 사유 (오답 진단)

차이를 유형으로 분류해 사유를 만듭니다. AI 없이 규칙으로 시작합니다.

| 유형 | 판별 | 사유 예 |
| --- | --- | --- |
| 차대 반대 | 변화의 부호만 전부 반대 | "차변과 대변이 서로 바뀌었어요" |
| 세액 포함 | 공급가액 계정이 공급가액+세액만큼 변함, 부가세 계정 변화 없음 | "세액 1,000,000원이 원재료 금액에 들어가 있어요" |
| 공제/불공제 혼동 | 불공 거래인데 부가세대급금 증가 | "이 지출의 매입세액은 공제받을 수 없어요. 증빙의 용도를 다시 보세요" |
| 계정 오류 (같은 분류) | 기대 계정 대신 같은 중분류의 다른 계정 | "비용인 것은 맞아요. 제조 쪽 비용인지 판매관리 쪽인지 보세요" |
| 계정 오류 (다른 분류) | 자산 ↔ 비용 등 | "이 지출은 올해 비용이 아니라 자산으로 남습니다" |
| 거래처 오류 | 계정 합계는 맞고 거래처별 변화가 다름 | "금액은 맞는데 거래처가 달라요" |
| 일자·기간 | 전표 일자 ≠ 증빙 일자 | "전표 일자는 작성일이 아니라 거래일입니다" |
| 금액 | 위에 해당하지 않는 금액 차이 | 차액 표시 |

오답 유형마다 "틀린 전표 → 기대하는 사유" 픽스처 테스트를 둡니다.

## 9. 완성도를 높이는 것

| 항목 | 내용 |
| --- | --- |
| **콘텐츠 검증을 CI로** | 모든 미션의 정답이 ERP 검증을 통과하는가 · 전체 재생 결과가 정답 재무제표와 같은가 · 오답 픽스처가 기대한 사유를 내는가. 콘텐츠가 엔진과 어긋나면 머지되지 않는다 |
| **완주 E2E** | 브라우저 자동화로 0장부터 수료까지 한 번에 통과하는 테스트. "튜토리얼이 중간에 막히지 않는다"를 보증 |
| **1분 안에 첫 미션** | 가입·설치 없이 체험 시작. 이메일 연결은 나중에 선택 |
| **근거 표시** | 미션 해설마다 근거(기업회계기준, 부가가치세법 조문, 기준 연도)를 단다. 세법은 해마다 바뀌므로 "2026년 기준"을 명시 |
| **실무자 검수** | 과정 공개 전에 현업 회계 담당자에게 흐름과 용어를 검토받는다. 이 사이트의 신뢰도는 코드가 아니라 콘텐츠의 정확성에서 나온다 |
| **학습 데이터로 개선** | 미션별 통과율·평균 제출 횟수·오답 유형 분포를 보고 어려운 미션의 힌트와 설명을 고친다 |
| **수료 리포트** | 처리한 전표 수, 장별 정확도, 자주 낸 오답 유형, 완성한 재무제표 |
| **틀려도 안전** | 장 단위 다시 시작, 정답 보고 넘어가기. 막혀서 그만두는 지점을 없앤다 |
| (나중) AI 튜터 | 규칙으로 못 잡는 오답에 대한 설명, 자유 질문. 규칙 기반 진단이 자리 잡은 뒤에 붙인다 |

### 단계 (안)

기간은 주 10시간 기준의 어림이며, 실습 층을 처음 만드는 L1의 실제 소요를 보고 다시 잡습니다.

| 순서 | 내용 | 기간 (안) |
| --- | --- | --- |
| 2단계 마무리 | 전기분 재무상태표, 시나리오 리플레이어 + 1년치 골든 테스트 | ~11월 말 |
| **L1. 세로 조각** | 게스트 입장, 실습 회사 생성, 미션 엔진과 채점, 미션 패널, 증빙 뷰어 3종, **0~1장** | 12월 |
| 첫 공개 | 서버 준비되는 대로 L1을 배포 (로그인 시도 제한, 게스트 정리 포함) | 서버 일정에 따름 |
| 3단계 + 4·5장 | 장부·시산표 / 판독·대사·월 마감 미션 | 2027-01 |
| 4단계 + 2·3·6장 | 매입매출·부가세 / 세금계산서 등 증빙 확장 | 02 |
| 5단계 + 7·8장 | 결산·재무제표·이월 | 03 |
| 6단계 + 9장 | 고정자산·권한 / 오류 찾기, 결재자 역할 | 04 초 |
| 7단계 | 성능, 완주 E2E, 콘텐츠 검수, 수료 리포트, 문서 | 04 |

**L1을 3단계보다 먼저 하는 이유**: 장부·결산 엔진은 어떻게 만들지 이미 알고 있지만, "미션으로 실무를 가르치는 경험"이 실제로 괜찮은지는 만들어 봐야 압니다. 가장 불확실한 것을 가장 먼저 작게 확인합니다. 1장은 일반전표만 쓰므로 지금 있는 엔진으로 충분합니다 (채점에 필요한 잔액 조회 하나만 추가).

## 11. 하지 않을 것

- 실제 세무 신고·세무 상담 (교육용임을 화면에 고지)
- 급여·4대 보험 **계산** (급여대장은 주어진 자료로 제공하고 전표 처리만 연습)
- 여러 회사·여러 업종 과정 (제조업 법인 하나로 완주가 먼저)
- 강의 영상, 결제, 커뮤니티, 실시간 협업
- 모바일에서의 전표 입력 (읽는 화면만 반응형, 입력은 데스크톱)

## 12. 위험과 대응

| 위험 | 대응 |
| --- | --- |
| **콘텐츠 분량과 정확성** — 가장 큰 일이 코드가 아니라 미션 작성 | 기존 시나리오 47건 재사용, 미션 형식을 파일로 고정, 장 단위로 엔진과 함께 출시, 실무자 검수 |
| **범위 폭발** | L1에서 한 장을 끝까지 만든 뒤 넓힌다. §11을 지킨다 |
| **정답이 여러 개인 거래** | 잔액 변화로 채점 + `accept`로 대안 분개 인정 |
| **실습 회사 정리와 불변식 2의 충돌** — 전기된 전표는 지울 수 없는데 게스트 회사는 지워야 한다 | 다시 시작 = 새 회사 생성. 버려진 실습 회사는 정리 배치만 회사 단위로 통째 삭제할 수 있게 하고, 그 경로를 ADR과 테스트로 고정 |
| **공개 사이트 남용** | 게스트 생성 속도 제한, 회사당 전표 수 상한, 미사용 게스트 자동 정리 |
| **세법 개정** | 과정에 기준 연도를 박고, 근거 조문을 미션에 기록해 바뀐 곳을 찾기 쉽게 |
