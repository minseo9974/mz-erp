# ADR-0005: 쓰기는 JPA, 집계 읽기는 MyBatis

- 상태: 채택 (2026-11-09)

## 맥락
전표 입력은 "전표 + 라인 + 부가세 정보"를 하나의 도메인 객체로 검증하고 저장하는 일이라 객체 모델이 잘 맞는다.
반면 원장·시산표·재무제표는 GROUP BY, 윈도 함수, 기간 누계가 많은 SQL이고, 성능 튜닝도 SQL을 직접 봐야 한다.

## 결정
- 쓰기(전표, 기준정보, 고정자산): Spring Data JPA + 도메인 모델
- 읽기 집계(원장, 시산표, 재무제표, 부가세 신고서): MyBatis 매퍼
  - 한 화면에 들어오는 짧은 집계(예: 계정·거래처별 합계 `ledger/BalanceMapper`)는 인터페이스의 `@Select` 어노테이션
  - 조건에 따라 SQL이 달라지거나 길어지는 집계(시산표, 재무제표, 부가세 신고서)는 XML 매퍼 — 동적 SQL과 가독성 때문
  - (2026-11-11 보완: 처음에는 전부 XML로 적었으나, 첫 매퍼가 한 문장짜리라 어노테이션으로 썼고 기준을 위처럼 정함)
- 같은 트랜잭션에서 섞어 쓸 때는 JPA flush 후 MyBatis 조회

## 결과
- 좋은 점: 도메인 규칙은 객체에, 집계는 SQL에 — 각자 잘하는 일. 국내 ERP 현업에서도 흔한 조합
- 감수할 점: 두 가지 기술을 유지해야 함, flush 순서 실수 주의 → 통합 테스트로 확인
