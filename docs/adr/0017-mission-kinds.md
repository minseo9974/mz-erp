# ADR-0017: 미션에 종류(kind)를 두고, 종류마다 제출과 판정을 나눈다

- 상태: 채택 (2026-11-24)

## 맥락
지금 미션은 한 종류다: 시나리오 거래 1건 = 정답 분개 1개, 결재 요청 때 장부 잔액의 변화로 채점한다 (`Course.Mission`, `LearningService.submit`, ADR-0013).

[설계의 미션 유형](../design/training-site.md#미션-유형) 여섯 가지 중 이것으로 표현되는 것은 '전표 입력'뿐이다.

- 0장(입사 첫날)부터 막힌다. "외상매출금 기초 잔액이 가장 큰 거래처는?"(장부 판독)과 개념 확인 문항은 전표가 아니라 값이나 보기를 제출한다
- 정정 미션은 "이미 전기된 잘못된 전표"가 미션 시작 전에 있어야 하고, 원전표가 남아 있는지도 본다
- 대사(차이가 0이 되었나), 마감·신고(기간 CLOSED, 정리 전표가 있나), 종합 실전(한 달치를 모아 마감 때 한 번)도 판정이 다르다
- 콘텐츠 테스트도 전표 미션을 전제로 한다: 모든 미션에 통장 거래내역이 있어야 하고, 증빙 금액 = 정답 분개의 차변 합계

## 결정
미션에 `kind`를 두고, 종류마다 **무엇을 제출하는가**와 **무엇을 정답으로 보는가**를 나눈다. 적지 않으면 `entry`(지금의 미션)다.

| kind | 실습자가 하는 일 | 제출 | 정답의 원본 | 판정 | 필요한 때 |
| --- | --- | --- | --- | --- | --- |
| `entry` | 증빙을 보고 전표 작성 | 결재 요청 (임시 전표) | `scenario = N` 또는 `[N, M]` | 잔액 변화 (지금 채점기) | 있음 |
| `quiz` | 개념 확인 선택형 | 고른 보기 | TOML의 보기·정답 | 일치 | L1 (0장) |
| `lookup` | 장부·화면에서 값 찾기 | 값 (금액·거래처·계정) | TOML의 정답 + 확인 근거 | 일치 | L1 (0장) |
| `correction` | 잘못 전기된 전표 정정 | 결재 요청 | `seed`(잘못된 전표) + `scenario = N` | 잔액 변화(= 정답 − seed) + 원전표가 역분개됐나 | L1 (1장) |
| `reconcile` | 두 자료의 차이를 찾아 해소 | 결재 요청 | 빠진 거래 `scenario = N` | 잔액 변화 + 대사 차이 0 | 3단계 |
| `procedure` | 마감·신고처럼 순서가 있는 일 | "다 했어요" | 상태 조건 목록 | 상태 검사 (기간 CLOSED 등) | 3~5단계 |
| `batch` | 한 달치를 모아 처리 | 마감 때 한 번 | 시나리오 여러 건 | 잔액 변화의 합 + 건별 진단 | 6단계 |

- **채점기는 종류별 전략**으로 둔다 (`MissionGrader` 하나에 종류별 구현). 잔액 변화 채점기(`Grader`)는 entry·correction·reconcile·batch가 함께 쓴다
- **제출 API는 하나**: `POST /learning/attempts/{id}/submit`에 본문(고른 보기, 찾은 값)을 선택으로 받는다
- **lookup의 정답**은 TOML에 적되, 장부에서 확인할 근거(계정·거래처·기준일)를 함께 적는다. CI가 과정을 재생한 장부에서 같은 값이 나오는지 확인한다 — 시나리오가 바뀌어 정답이 어긋나면 머지되지 않는다
- **correction의 seed**는 시나리오가 아니라 과정 파일에 둔다. 미션을 시작하기 직전에 시스템이 전기한다 ("선배가 지난주에 올린 전표", "지난주의 내가 올린 전표"). 정정까지 하면 seed와 역분개가 상쇄되어, 시나리오 정답(골든 테스트)은 바뀌지 않는다. 정정 방법은 [ADR-0018](0018-reversal-request.md)
- **quiz**는 장마다 2~3개 이내 (설계 §4). 보기마다 "왜 아닌지" 한 줄을 둔다
- **오답 예시를 모든 종류에.** ADR-0015에서 CI가 확인하기로 하고 아직 만들지 않은 "미션마다 둔 오답 예시"를 여기서 형식으로 정한다:
  ```toml
  [[chapters.missions.mistakes]]
  lines = [["D", "817", 250000], ["C", "103", 250000]]    # entry·correction: 틀린 분개
  says  = "직원에게서 떼어 둔 세금은 회사의 비용이 아니에요. 장부에 맡아 둔 돈으로 올라가 있던 계정을 찾아보세요."
  ```
  제출한 변화가 오답 예시 중 하나와 같으면 그 미션 전용 사유를 먼저 보여 주고, 없으면 지금의 범용 사유를 쓴다. CI는 오답 예시마다 "통과하지 않고, 적어 둔 사유가 나온다"를 확인한다. 해설의 '흔한 실수'가 첫 재료다
- **증빙 규칙**: 통장 거래내역은 보통예금이 움직이는 미션에만 두고, 날짜순 재생에서 만든다 ([ADR-0016](0016-course-follows-calendar.md)). 증빙 금액 검사는 종류별로
- **DB**: 종류는 콘텐츠에서 오므로 `mission_attempt`에 저장하지 않는다. `attempt_submission`에 제출 값(JSON)을 더한다 — quiz·lookup의 오답 분포를 보려고

## 결과
- 좋은 점
  - 0장·정정·대사·마감·실전이 모두 같은 수명주기(시작 → 제출 → 승인/반려 → 해설 → 다시 보기·다시 풀기)를 쓴다
  - 미션 전용 반려 사유가 생긴다. 지금의 범용 사유("계정 하나가 맞지 않아요")보다 신입에게 훨씬 구체적이다
  - ADR-0015의 오답 예시 CI가 실제로 생긴다
- 감수할 점
  - 종류마다 채점기, 미션 패널의 입력 칸, 콘텐츠 테스트가 따로 필요하다. L1에는 entry·quiz·lookup·correction 네 가지만 만든다
  - 과정 파일 형식이 바뀌므로 `CourseCatalog`의 검증과 콘텐츠 테스트를 같이 고친다
- 면접 포인트: "채점 방식이 늘어날 때 미션 엔진을 어떻게 확장했나" (전략 패턴, 콘텐츠와 판정의 분리)
